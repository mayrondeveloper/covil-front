# Context Mesh Framework

Framework de documentação viva para projetos assistidos por IA. Gira em torno de 3 fases — **Intent → Build → Learn** — e impõe separação rígida de tipos de arquivo para que agentes possam navegar e manter o contexto de forma confiável.

## Fases

1. **Intent**: capturar *o quê* e *por quê* antes de codar. Cria `feature-*.md` (funcional) e `decisions/*.md` (técnico).
2. **Build**: implementar seguindo as decisões. Usar `knowledge/patterns/*.md` como referência de como implementar.
3. **Learn**: após mudanças, atualizar `Outcomes` das decisões, o `changelog.md`, e criar `learning-*.md` quando houver insights relevantes.

## Tipos de arquivo (separação obrigatória)

| Tipo | Onde | O que contém | O que NÃO contém |
|---|---|---|---|
| Feature | `context/intent/feature-*.md` | O que a feature faz (usuário), por que existe (valor), critérios de aceitação funcionais | Detalhes técnicos, libs, código |
| Decision | `context/decisions/NNN-*.md` | Escolha técnica (lib, framework, abordagem), racional, alternativas, outcomes | Descrição de funcionalidade, código de exemplo |
| Pattern | `context/knowledge/patterns/*.md` | Código de exemplo, estrutura reutilizável, como implementar | Por que o projeto existe, escolha de stack |
| Anti-pattern | `context/knowledge/anti-patterns/*.md` | Abordagens a evitar e por quê | - |
| Agent | `context/agents/*.md` | Prompts e instruções específicas para agentes IA | - |
| Evolution | `context/evolution/*.md` | Changelog, aprendizados, mudanças ao longo do tempo | - |

### Exemplos de separação correta

❌ **Errado** (tudo no feature):
> ## What: SEO usando Next.js Metadata API, Open Graph tags, structured data...

✅ **Certo**:
- `feature-seo.md` → "Melhorar visibilidade em buscadores" + links
- `decisions/002-seo-approach.md` → "Usar Next.js Metadata API porque..."
- `knowledge/patterns/seo-metadata.md` → código de exemplo

## Padrão Plan → Approve → Execute (obrigatório)

1. **Plan**: agente lê contexto relevante (`@context/...`) e propõe plano referenciando features/decisions/patterns.
2. **Approve**: humano aprova. Sem aprovação, sem código.
3. **Execute**: implementar seguindo o plano aprovado.

## Quando criar / não criar arquivos

**Criar feature** quando: há funcionalidade distinta com valor para o usuário.
**Criar decision** quando: escolha técnica não-óbvia foi feita (lib, arquitetura, padrão).
**Criar pattern** quando: um jeito de fazer se repete e vale ser reutilizado.
**Não criar** arquivos para: operações triviais, escolhas óbvias, detalhes de implementação que não se repetem.

## Definition of Done (fase Build)

- [ ] Decision existe antes da implementação
- [ ] Código segue patterns documentados
- [ ] Decisões respeitadas
- [ ] Testes passando
- [ ] Contexto atualizado refletindo mudanças
- [ ] `changelog.md` atualizado

## Links bidirecionais (regras)

- Feature → Decision: "Related: [Decision: X](../decisions/NNN-x.md)"
- Decision → Feature: "Related: [Feature: Y](../intent/feature-y.md)"
- Feature → Pattern, Pattern → Decision, etc., sempre que houver relação real.
- Se o link existe num sentido, deve existir no outro.

## Seção Status (obrigatória em todo arquivo)

```
## Status
- **Created**: YYYY-MM-DD (Phase: Intent|Build|Learn)
- **Status**: Draft|Active|Accepted|Superseded|Deprecated
- **Note**: (opcional)
```
